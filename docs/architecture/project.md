# Архитектура проекта и Code Style

## Назначение документа

Документ фиксирует фактическое техническое устройство проекта и соглашения, которым должен соответствовать новый код. Функциональные требования к редактору находятся в [`docs/editor`](../editor/), а их индекс — в [`docs/agent.md`](../agent.md).

## Технологический стек

- React 19 и React DOM;
- TypeScript 6;
- Vite 8;
- Tiptap 3 и ProseMirror — основа разрабатываемого редактора;
- документация BlockNote — reference для модели и поведения, без runtime-зависимости;
- Material UI — оболочка приложения и toolbar Tiptap;
- Oxlint — статический анализ;
- Vitest, jsdom и React Testing Library — проверки модулей и интеграции;
- npm и `package-lock.json` — управление зависимостями.

Проект использует ES modules: в `package.json` установлено `"type": "module"`.

## Публичный компонент

- `TiptapEditor` является единственным публичным React-компонентом пакета.
- Компонент содержит редактор, formatting toolbar, меню блоков и кнопки undo/redo.
- `initialBlocks` задаёт начальный документ при создании экземпляра.
- `onChange` получает актуальный публичный массив `Block[]` после изменений.
- Не должен отдавать наружу внутренний Tiptap JSON как публичный формат документа.
- Преобразует публичную блочную модель во внутреннюю схему Tiptap при инициализации и обратно для `onChange`.
- Расширения Tiptap отвечают за структуру узлов, marks, команды и обеспечение инвариантов.

## Слои данных

В проекте существуют два представления документа.

### Публичное представление

Публичный формат соответствует спецификациям редактора:

```ts
type Block = {
  id: string
  type: string
  props: Record<string, unknown>
  content: InlineContent[] | unknown
  children: Block[]
}
```

Для `paragraph` используются `DefaultProps`, `InlineContent[]` и рекурсивный массив `children`. Для `quote` используются `backgroundColor`, `textColor`, `InlineContent[]` и тот же рекурсивный массив `children`; `textAlignment` в публичную модель Quote не входит.

### Внутреннее представление Tiptap

Текущая схема ProseMirror:

```text
doc
└── blockContainer+
    ├── paragraph | heading | quote | bulletListItem | numberedListItem | checkListItem
    └── blockGroup?
        └── blockContainer+
```

- `blockContainer` хранит `id` и props блока.
- Узел содержимого хранит inline content и определяет публичный тип блока; heading level, numbered start и checklist checked находятся в атрибутах соответствующего узла.
- `blockGroup` хранит дочерние блоки.
- `doc` содержит минимум один блок.

Преобразования между представлениями должны быть изолированы от React-компонентов и не терять поддерживаемые данные.

## Инварианты блочной модели

- Каждый `blockContainer` имеет непустой UUID v7.
- ID уникален во всём документе, включая вложенные блоки.
- Редактирование и перемещение блока сохраняют ID.
- Новый или скопированный блок получает новый ID.
- Документ всегда содержит минимум один блок.
- Paragraph всегда содержит узел `paragraph`, а Quote — узел `quote`, даже если блок пуст.
- Дочерние блоки существуют только внутри `blockGroup` своего родителя.
- Публичное `content` не включает содержимое `children`.

Плагин контроля ID обязан восстанавливать отсутствующие идентификаторы и устранять дубликаты. Генерация ID и нормализация не должны создавать бесконечные append-транзакции.

## Inline content

Текст представлен узлами Tiptap `text`, а свойства `StyledText.styles` — marks.

Текущее соответствие:

| Публичная модель | Tiptap |
| --- | --- |
| `bold` | mark `bold` |
| `italic` | mark `italic` |
| `underline` | mark `underline` |
| `strike` | mark `strike` |
| `code` | mark `code` |
| `textColor` | mark `textColor` |
| `backgroundColor` | mark `backgroundColor` |
| `Link` | mark `link` и сгруппированные `StyledText` |

При сериализации соседние текстовые сегменты с одинаковыми стилями нормализуются. Marks, относящиеся к ссылке, не должны попадать в объект `styles`.

## Хранение состояния

Компонент не выбирает ключ и расписание сохранения: приложение-потребитель
передаёт данные через `initialBlocks` и получает изменения через `onChange`.
Пакет экспортирует чистые persistence-адаптеры. Backend использует плоский
`FlatBlock[]` с `parentId` и соседними ссылками, а `localStorage` — публичный
nested `Block[]`. Полный контракт, валидация и предел глубины описаны в
[children.md](../editor/children.md).

## Code Style

### TypeScript

- Новый код пишется на TypeScript со строгой типизацией предметной модели.
- Не использовать `any`, если тип возможно выразить через union, generic или `unknown` с проверкой.
- Для данных применять `type`; `interface` допустим для расширяемых публичных контрактов.
- Использовать discriminated unions для блоков и inline content (`type: "paragraph"`, `type: "text"`, `type: "link"`).
- Использовать `import type` для импортов, существующих только на уровне типов.
- Не подавлять ошибки TypeScript без комментария с технической причиной.
- Все варианты union должны обрабатываться исчерпывающе либо иметь явно обоснованный fallback.

### Именование

- React-компоненты, типы и Tiptap extensions: `PascalCase`.
- Функции, переменные и свойства: `camelCase`.
- Константы уровня модуля: `UPPER_SNAKE_CASE`, если это неизменяемый технический ключ; объектные конфигурации могут иметь `camelCase`.
- Имена файлов компонентов: `PascalCase.tsx`.
- Имена документов и будущих обычных модулей: `kebab-case`.
- Имена узлов и marks Tiptap должны быть стабильны и совпадать с сериализуемыми техническими именами.

### Форматирование

- Использовать одинарные кавычки в TypeScript/TSX.
- Точки с запятой не ставить, что соответствует текущему коду.
- Сохранять завершающие запятые в многострочных массивах, объектах и вызовах.
- Разбивать длинные JSX-элементы, конфигурации extensions и callback-функции на читаемые многострочные конструкции.
- Не объединять независимые операции в трудночитаемые однострочные выражения.
- Комментарии должны объяснять причину или ограничение, а не пересказывать код.

### React

- Использовать функциональные компоненты и hooks.
- Не хранить в React state данные, которыми уже владеет Tiptap.
- Побочные эффекты редактора размещать в lifecycle/callback API редактора.
- UI-компонент не должен содержать предметную сериализацию, если её можно вынести в чистые функции или отдельный модуль.
- Кнопки без текстовой подписи должны иметь `aria-label`.
- Недоступные действия должны иметь корректное состояние `disabled`.

### Tiptap и ProseMirror

- Инварианты документа реализовывать на уровне schema/extensions/plugins, а не исправлять DOM после рендера.
- Не обращаться к DOM как к источнику данных редактора.
- Команды должны возвращать `true`, только если действие обработано.
- Транзакции должны сохранять selection и не терять attrs, marks или дочерние блоки.
- Позиции ProseMirror необходимо вычислять относительно текущего `Transaction.doc`, если предыдущие шаги транзакции могли изменить документ.
- Парсинг и рендеринг HTML должны быть взаимно совместимы для поддерживаемых данных.
- Публичный формат нельзя связывать с деталями `JSONContent` сильнее необходимого.

### CSS

- Глобальные reset и базовые правила размещаются в `index.css`.
- `App.css` содержит локальный пример; `tiptap/editor.css` — базовые блоки и оболочку Tiptap. Стили списков, drag-and-drop, меню и toolbar находятся рядом с соответствующими модулями.
- CSS подключается один раз владельцем или компонентом композиции редактора. Media queries располагаются вместе с правилами своих компонентов. Селекторы ограничиваются классами редактора (`.tiptap*`, `.bn-*`).
- Общая переменная `--tiptap-first-line-height` задаётся в `editor.css` и используется боковыми кнопками.
- Содержимое элементов списка находится в `.tiptap-list-item-content`, отдельно от маркера или checkbox: тексту нужен собственный строчный контекст внутри flex-контейнера. Служебный `.ProseMirror-trailingBreak:only-child` отображается как `inline-block`, чтобы браузер рисовал нативную каретку в пустом блоке; символы-заполнители в документ не добавляются.
- Не использовать общие селекторы, способные изменить поведение обоих редакторов случайно.
- Сохранять доступный focus state и адаптивность для узких экранов.
- Значения block props должны задаваться через schema/rendering, а не через позиционные CSS-селекторы.

## Организация кода по мере роста

Код группируется по возможностям внутри `src/editors/tiptap`. Новый блок получает собственную папку с узлом, обработчиками и внешним `index.ts`. Общие операции размещаются в `blocks/shared` только при совпадающем поведении. Обработчики Enter paragraph, heading и quote остаются отдельными: правила props, selection и переноса children различаются.

`schema` описывает структурный каркас, `marks` — inline-оформление, `extensions` — общие инварианты и поведение. `BlockBehavior` сохраняет приоритет 1000 и подключает обработчик цитаты из `blocks/quote/quote-enter.ts`. Фабрика `createEditorExtensions` сохраняет порядок регистрации и настройки StarterKit.

`serialization/blocks.ts` использует чистые inline-преобразования из `inline.ts`. Сериализация и schema не зависят от React, DOM или способа хранения данных.

### Владельцы состояния

- `menu/menu-state.ts` владеет ключом плагина и переходами состояния; `menu-commands.ts` — командами; `menu-input.ts` — событиями. Decorations и доступность выделены отдельно. `BlockMenu.ts` собирает плагин, React-представление импортирует состояние и команды напрямую.
- `drag-and-drop/drag-session.ts` владеет активной сессией и очисткой preview. Операции `getActiveDrag`, `startDrag`, `endDrag` не экспортируют изменяемую переменную. Сессия общая между экземплярами редактора для межредакторного переноса; состояние курсора остаётся локальным в плагине.
- `drop-handler.ts` выполняет перенос и получает callback завершения, поэтому не зависит от файла сборки плагина. `drag-decorations.ts` получает позицию курсора аргументом.
- `use-block-type-select.ts` владеет anchor и сохранённым selection. Toolbar сохраняет одну общую подписку на состояние форматирования и передаёт нужные значения группам кнопок.

### Направление импортов и размер модулей

Сборка редактора зависит от функциональных модулей; они используют нижние общие типы и операции. Состояние не импортирует команды или UI. Внутренние импорты направляются на конкретные файлы; `index.ts` используется на внешних границах функциональных папок. Циклические зависимости не допускаются.

Ориентир — 100–150 физических строк для законченной ответственности, включая импорты и пустые строки. Сокращать форматирование ради лимита не следует. Связный `types.ts` остаётся единым описанием публичной модели. Если модуль превышает 150 строк, следует рассмотреть смысловое разделение и документировать причину сохранения целого файла.

## Зависимости

- Добавлять пакет только при отсутствии подходящей возможности в текущем стеке.
- Runtime-зависимости размещать в `dependencies`, инструменты сборки и проверки — в `devDependencies`.
- После изменения зависимостей обновлять и `package.json`, и `package-lock.json` через npm.
- Не импортировать транзитивную зависимость без её явного объявления в `package.json`.
- Версии пакетов Tiptap должны оставаться согласованными.

## Проверки перед завершением изменения

Минимальный набор:

```bash
npm run lint
npm run build
```

Для изменений поведения редактора дополнительно требуется ручная или автоматизированная проверка затронутых сценариев в браузере:

- создание и редактирование блока;
- стабильность и формат ID;
- сериализация и повторная загрузка;
- undo/redo;
- отсутствие ошибок в консоли;
- соответствующие критерии приёмки из `docs/editor/`.

Автоматические проверки описаны в [руководстве по тестированию](testing.md). Тесты лежат рядом с модулями, общие helpers — в `src/test`. Кроме lint/build выполняются `npm test`, `npm run test:types` и `npm run test:coverage`. Runtime-файлы компилируются app-конфигурацией, тесты и Vitest config — отдельной `tsconfig.test.json`.

Применяются следующие уровни проверки:

- unit-тесты для генерации ID, нормализации и сериализации;
- интеграционные тесты ProseMirror transactions и commands;
- browser/e2e-тесты для клавиатуры, selection, clipboard и drag-and-drop;
- дифференциальные сценарии, сравнивающие BlockNote и Tiptap.

## Известные технические ограничения

- Проект пока является playground, а не опубликованной библиотекой.
- Публичный API надстройки над Tiptap ещё не выделен.
- Публичные типы находятся в `tiptap/types.ts`, преобразования — в `tiptap/serialization`.
- Реализованы узлы `paragraph`, `heading`, `quote`, `bulletListItem`, `numberedListItem`, `checkListItem`; соответствие всем сценариям спецификаций остаётся частичным.
- Изменение вложенности через отдельный UI для Tiptap ещё не реализовано.
- Drag-and-drop блоков реализован расширением
  `src/editors/tiptap/drag-and-drop/DragAndDrop.ts`: оно добавляет drag handle,
  preview, drop cursor, перенос одного или выбранного диапазона блоков,
  межредакторный перенос и клавиатурное перемещение.
- Vitest покрывает модули редакторов, ProseMirror transactions и React-компоненты в jsdom. Нативный drag, layout, IME и реальный browser focus требуют отдельной проверки. Исторический сравнительный Node-стенд в OpenSpec change сохраняется; новый suite от него не зависит.
- Совместное редактирование и серверное хранение не подключены.

Эти ограничения описывают текущее состояние, но не отменяют требования функциональных спецификаций.
