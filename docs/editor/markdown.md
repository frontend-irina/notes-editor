# Импорт и экспорт Markdown

## Назначение

Документ определяет контракт преобразования между публичной блочной моделью
редактора и Markdown. Реализация надстройки над Tiptap должна быть совместима с
наблюдаемым поведением BlockNote для поддерживаемого подмножества Markdown.

Источники поведения:

- [BlockNote — Markdown Import](https://www.blocknotejs.org/docs/features/import/markdown);
- [BlockNote — Markdown Export](https://www.blocknotejs.org/docs/features/export/markdown);
- [BlockNote — Format Interoperability](https://www.blocknotejs.org/docs/foundations/supported-formats).

Связанные спецификации:

- [HTML](./html.md);
- [Inline Content](./inline-content.md);
- [Paragraph](./blocks/paragraph/paragraph.md);
- [Markdown для Paragraph](./blocks/paragraph/markdown.md);
- [Heading](./blocks/heading.md);
- [Quote](./blocks/quote.md).

## Роль формата

Markdown является обменным, а не каноническим форматом документа.

- Импорт и экспорт Markdown считаются **lossy-преобразованиями**.
- Markdown не способен представить все типы блоков, props, inline-стили,
  вложенность и служебные данные редактора.
- Каноническим форматом хранения остаётся публичный массив `Block[]` в JSON.
- Markdown нельзя использовать для резервного сохранения документа, если
  требуется точное восстановление `id`, props или неподдерживаемых конструкций.
- Потери должны быть детерминированными и не должны приводить к ошибке всего
  преобразования, если отдельная конструкция может быть безопасно упрощена.

## Поддерживаемый диалект

Минимальный формат ориентирован на общее подмножество CommonMark и базовых
возможностей GFM:

- paragraphs;
- headings;
- ordered и unordered lists;
- task lists;
- blockquotes;
- fenced code blocks;
- tables;
- links;
- images;
- bold и italic;
- strikethrough;
- hard breaks.

Поддержка всех диалектов Markdown не является целью редактора. В частности,
не следует автоматически обещать полную совместимость с MDX, Pandoc,
директивами, footnotes, front matter, embedded JSX/HTML или расширениями
конкретных платформ.

Если продукту требуется более широкий диалект, рекомендуемый pipeline:

```text
Markdown → внешний parser → HTML → импорт HTML → Block[]
```

Правила промежуточного HTML определены в [html.md](./html.md).

## Публичный API

Совместимый API надстройки должен предоставлять асинхронно-безопасные операции с
эквивалентной семантикой:

```ts
type MarkdownImportResult = {
  blocks: Block[];
  warnings: MarkdownDiagnostic[];
};

type MarkdownExportResult = {
  markdown: string;
  warnings: MarkdownDiagnostic[];
};

type MarkdownDiagnostic = {
  code: string;
  message: string;
  severity: "warning" | "error";
  sourceRange?: {
    from: number;
    to: number;
  };
  blockId?: string;
};

function importMarkdown(markdown: string): MarkdownImportResult;
function exportMarkdown(blocks?: Block[]): MarkdownExportResult;
```

На уровне совместимости с BlockNote этим операциям соответствуют:

```ts
editor.tryParseMarkdownToBlocks(markdown: string): Block[];
editor.blocksToMarkdownLossy(blocks?: Block[]): string;
```

- Если `blocks` при экспорте не переданы, экспортируется весь документ.
- Преобразование не должно напрямую зависеть от React-компонентов или DOM
  редактора.
- API не должен изменять переданные `blocks` или текущий документ как побочный
  эффект.
- Замена документа результатом импорта является отдельной явной операцией.

## Импорт Markdown

### Общие правила

- Входом является строка Markdown в UTF-8/JavaScript string.
- Результатом является нормализованный массив публичных блоков.
- Неизвестная inline-разметка импортируется как обычный текст, если это возможно.
- Неизвестная блочная конструкция упрощается до поддерживаемых blocks без потери
  читаемого текста, если это возможно.
- Импортируемые блоки получают новые UUID v7 по правилам
  [block-id.md](./block-id.md), поскольку Markdown не содержит внутренних `id`.
- Импорт не должен доверять встроенному HTML или URL как безопасным только потому,
  что они пришли из Markdown.
- Пустой или содержащий только пробельные символы ввод должен приводить к
  корректному пустому документу согласно инварианту схемы, а не к исключению.

### Блочное соответствие

| Markdown | Публичная модель |
| --- | --- |
| Обычный текстовый абзац | `paragraph` |
| `#` … `######` | `heading` с `level: 1` … `6` |
| `-`, `*`, `+` | `bulletListItem` |
| `1.` | `numberedListItem` |
| `- [ ]`, `- [x]` | check/task list item с соответствующим checked-state |
| `>` | `quote` |
| fenced code | code block с языком, если он распознан |
| GFM table | table block, если он присутствует в активной схеме |
| image syntax | image block или совместимое inline-представление схемы |

- Конструкция создаётся как специализированный block только если соответствующий
  тип зарегистрирован в активной схеме.
- При отсутствии типа содержимое должно быть преобразовано в ближайшее безопасное
  поддерживаемое представление, обычно paragraph/plain text, с diagnostic warning.
- Вложенность списков восстанавливается в `children` настолько, насколько она
  однозначно выражена отступами Markdown.

### Inline-соответствие

| Markdown | `InlineContent` |
| --- | --- |
| `**text**` / `__text__` | `bold: true` |
| `*text*` / `_text_` | `italic: true` |
| `~~text~~` | `strike: true` |
| `` `text` `` | `code: true` |
| `[label](href)` | `Link` |
| hard break | поддерживаемый перенос строки |

- Стили могут комбинироваться и должны нормализоваться согласно
  [inline-content.md](./inline-content.md).
- Markdown не имеет стандартного переносимого синтаксиса для `underline`,
  `textColor` и `backgroundColor`; эти стили могут быть потеряны.
- Ссылка сохраняет отображаемый текст и `href`, но служебные атрибуты ссылки,
  отсутствующие в публичной модели, не сохраняются.

## Экспорт Markdown

### Общие правила

- Экспорт создаёт читаемый Markdown без служебной разметки редактора.
- `id` блока не экспортируется.
- Стандартные props без Markdown-эквивалента не экспортируются.
- Экспорт не должен генерировать HTML только ради сохранения внутренних props,
  если выбран режим совместимого Markdown.
- Последовательный экспорт одного нормализованного документа должен быть
  детерминированным.

### Потери при экспорте

Минимально ожидаемые потери:

- `backgroundColor`, `textColor` и `textAlignment` уровня блока;
- inline `underline`, `textColor` и `backgroundColor`;
- UUID и другие служебные attrs;
- toggle-состояние и toggle-возможность heading;
- свойства пользовательских blocks без Markdown-представления;
- вложенность детей у blocks, которые Markdown не может корректно вкладывать.

Как и в BlockNote, дети blocks, не являющихся list items, могут быть выведены как
последующие невложенные блоки. Такое упрощение обязательно должно быть отмечено
diagnostic warning в расширенном API.

### Экранирование

- Символы, имеющие структурное значение в текущем контексте Markdown, должны быть
  экранированы так, чтобы повторный импорт не менял обычный текст на разметку.
- Backticks inline code и fence code block должны выбирать корректный размер
  delimiter, если содержимое уже включает backticks.
- Текст ссылки, URL, скобки и обратные слэши должны экранироваться
  контекстно-зависимо.
- Экспорт не должен добавлять лишнее экранирование, меняющее отображаемый текст.

## Quote

Модель блока и его интерактивное поведение определены в
[quote.md](./blocks/quote.md). В Markdown блок `quote` представлен CommonMark
blockquote.

### Импорт

- Строка с маркером `>` создаёт блок `quote`, если тип зарегистрирован в активной
  схеме. Пробел после маркера рекомендуется, но не является обязательным для
  валидного CommonMark blockquote.
- Маркеры `>` не входят в `InlineContent[]`; текст, ссылки и поддерживаемые
  inline-стили внутри цитаты преобразуются по общим правилам Markdown.
- Продолжающиеся строки одного простого blockquote объединяются в content одного
  Quote с нормализованными soft/hard breaks.
- Пустой blockquote создаёт Quote с `content: []`.
- Markdown не содержит ID и block props Quote. Импортированный блок получает
  новый UUID v7, а `backgroundColor` и `textColor` принимают значение
  `"default"`.
- Если blockquote содержит несколько block-level конструкций, реализация должна
  сохранить их читаемый текст и порядок. Так как один Quote допускает только
  `InlineContent[]`, неоднозначная структура нормализуется в последовательность
  поддерживаемых blocks и сопровождается warning.
- Дополнительный уровень `>` считается вложенным blockquote. Он восстанавливается
  через `children` только когда mapping в публичную блочную модель однозначен;
  иначе вложенность безопасно упрощается с warning, без потери читаемого текста.

### Экспорт

- Каждая физическая строка inline content Quote получает префикс `> `; пустая
  строка внутри цитаты сериализуется как строка `>`.
- Поддерживаемые inline-стили и ссылки сериализуются после маркера по общим
  правилам экспорта.
- Quote отделяется от соседних top-level blocks пустой строкой, чтобы повторный
  импорт не объединял независимые blocks.
- `id`, `backgroundColor` и `textColor` не экспортируются: переносимого
  CommonMark-представления для них нет.
- `children` Quote относятся к блочной структуре, а не к его inline content. Если
  выбранный BlockNote-совместимый lossy exporter выводит их следом как top-level
  blocks, потеря вложенности должна сопровождаться warning.

Канонический простой пример:

```md
> Текст с **жирным** начертанием и [ссылкой](https://example.com).
```

Для простого Quote гарантируется семантический цикл
`quote → Markdown → quote`: сохраняются тип, текст и поддерживаемое inline-
форматирование; новый ID и default block colors считаются ожидаемой нормализацией.

## Элементы списка

Модель list-item blocks описана в [list-types.md](./blocks/list-types.md).

### Импорт

| Markdown | Публичная модель |
| --- | --- |
| `- пункт`, `* пункт`, `+ пункт` | `bulletListItem` |
| `1. пункт` или `1) пункт` при поддержке парсером | `numberedListItem` |
| `- [ ] задача` | `checkListItem` с `checked: false` |
| `- [x] задача` / `- [X] задача` | `checkListItem` с `checked: true` |

- Исходный bullet marker не хранится: `-`, `*` и `+` создают один тип блока.
- Начальное число ordered list становится `start` первого элемента;
  автоматически продолжающиеся номера следующих элементов могут быть опущены.
- Отступы преобразуются в `children` ближайшего родительского list item по
  правилам выбранного CommonMark/GFM parser.
- Маркер и `[ ]` / `[x]` не входят в `content`. Task-list синтаксис распознаётся
  только внутри list item.
- Стандартный CommonMark/GFM не создаёт `toggleListItem` без отдельного расширения.
- Отсутствующий в активной схеме тип заменяется безопасным fallback с warning.

### Экспорт

```md
- Маркированный пункт
  3. Вложенный нумерованный пункт
- [ ] Невыполненная задача
- [x] Выполненная задача
```

- `bulletListItem` использует единый канонический marker; исходный marker после
  round trip сохранять не требуется.
- `numberedListItem` использует числовой marker. Явный `start` первой группы
  задаёт начальное число; автоматически продолжающиеся номера нормализуются.
- Разрыв нумерации начинает новую Markdown-группу либо создаёт diagnostic о потере
  точного номера.
- `checkListItem` экспортируется как `[ ]` при `false` и `[x]` при `true`.
- Дочерние list items получают корректный отступ под родительским marker.
- Непредставимые вложенные blocks могут быть выведены после списка с warning.
- `toggleListItem` экспортируется как обычный list item с доступными детьми и
  warning; toggle-возможность и состояние раскрытия теряются.

### Round trip и потери

Цикл `Markdown → Block[] → Markdown → Block[]` сохраняет порядок, читаемый текст,
поддерживаемую вложенность, тип bullet/numbered/check list и `checked`. Допустима
нормализация marker, разделителя ordered list, автоматически продолжающихся
номеров, отступов, пустых строк и эквивалентной inline-разметки.

Markdown не сохраняет UUID, `DefaultProps`, toggle-возможность и локальное
toggle-состояние. Произвольные разрывы нумерации также могут быть потеряны, если
выбранный диалект не позволяет представить их без HTML.

## Ошибки и diagnostics

- Синтаксически неоднозначный Markdown не должен приводить к падению редактора.
- Восстановимая проблема возвращает результат и warning.
- Невосстановимая проблема должна возвращать контролируемую ошибку без частичной
  замены текущего документа.
- Diagnostics не входят в публичный документ и не сохраняются в `localStorage`.
- UI самостоятельно решает, показывать warnings пользователю или журналировать их.

## Безопасность

- Встроенный HTML, ссылки и URL изображений считаются недоверенными данными.
- Импорт не должен выполнять scripts, event handlers или произвольный код.
- Опасные URL-схемы должны отклоняться или нейтрализоваться общей URL-политикой.
- Экспорт не является sanitizer для данных, которые затем интерпретирует другой
  Markdown renderer.
- Приложение обязано использовать безопасный renderer при показе экспортированного
  Markdown вне редактора.

## Round trip и эквивалентность

Для Markdown гарантируется не побайтовая идентичность, а семантическая
эквивалентность поддерживаемого подмножества:

```text
Markdown → Block[] → Markdown → Block[]
```

После цикла должны сохраняться:

- порядок поддерживаемых blocks;
- текстовое содержимое;
- поддерживаемые типы и уровни headings;
- поддерживаемая вложенность списков;
- bold, italic, strike, code и ссылки;
- тип `quote` и его поддерживаемое inline content для простого blockquote;
- семантика task list и table, если эти blocks присутствуют в схеме.

Пробелы, delimiter style, нумерация ordered list, число пустых строк и другое
поверхностное форматирование могут быть нормализованы.

## Критерии приёмки

1. Импорт и экспорт явно считаются lossy и не используются как каноническое
   persistence-представление.
2. Импорт поддерживает документированное общее подмножество CommonMark/GFM.
3. Неизвестный синтаксис сохраняется как читаемый текст или создаёт diagnostic,
   но не приводит к падению всего преобразования.
4. Импортированные blocks получают корректные уникальные UUID v7.
5. Headings 1–6, paragraphs, lists, task lists, tables, code, quotes, links,
   images, emphasis, strikethrough и hard breaks преобразуются при наличии типов
   в схеме.
6. Неподдерживаемые props и стили теряются предсказуемо и документированно.
7. Экспорт без аргумента обрабатывает весь документ; экспорт переданного массива
   — только этот массив.
8. Экспорт корректно экранирует структурные символы Markdown.
9. Round trip сохраняет семантику поддерживаемого подмножества.
10. Импорт не выполняет встроенный HTML или небезопасные URL.
11. Ошибка импорта не приводит к частичной неявной замене текущего документа.
12. Расширенный API предоставляет warnings для выполненных lossy-преобразований.
13. Простой Quote импортируется из `>` и экспортируется с маркером на каждой
    строке; ID и block colors предсказуемо теряются.
14. Неоднозначные многоабзацные и вложенные blockquotes не теряют читаемый текст и
    создают warning при упрощении структуры.

## Открытые вопросы для проверки по эталону

- точный результат импорта malformed Markdown;
- нормализация soft break и hard break;
- выбор bullet marker и ordered-list numbering при экспорте;
- поведение raw HTML внутри Markdown;
- экранирование сложных URL и nested emphasis;
- экспорт произвольных вложенных non-list blocks;
- mapping пользовательских blocks и inline content;
- точный round trip многострочных и вложенных blockquotes;
- сохранение языка fenced code block и alignment таблиц.
