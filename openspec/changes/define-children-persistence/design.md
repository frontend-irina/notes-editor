## Context

Публичный `Block` уже совместим с основной формой BlockNote: блок содержит ID,
тип, props, content и рекурсивный `children`. Текущая Tiptap-схема представляет
children через вложенный `blockGroup`, а сериализация уже рекурсивно преобразует
`Block <-> JSONContent`. Отдельного flat-контракта и общего ограничения глубины
нет.

BlockNote остаётся поведенческим ориентиром для дерева, навигации между parent и
siblings и depth-first обхода. Backend-формат и лимит глубины являются нашими
осознанными отличиями.

## Goals / Non-Goals

**Goals:**

- один источник истины для максимальной глубины;
- детерминированные и тестируемые `tree <-> flat` преобразования;
- nested JSON в `localStorage` и flat JSON на backend-границе;
- отсутствие каскадных update для неизменившихся descendants;
- предсказуемое сохранение данных при paste глубже лимита.

**Non-Goals:**

- реализация backend API, revision conflict и серверной идемпотентности;
- выбор debounce/max-wait политики автосохранения;
- collaborative editing или CRDT;
- изменение публичной формы `Block` и семантики inline content;
- копирование внутренней реализации BlockNote.

## Decisions

### 1. Глубина и константа

Константа располагается в нижнем, независимом от React модуле блочной модели и
экспортируется публично:

```ts
export const MAX_BLOCK_DEPTH = 5
```

Корневой массив не считается уровнем: его элементы имеют depth 1. Проверки nest,
drop, paste/import, загрузки backend и `localStorage` используют одну константу.
Локальные литералы `5` в структурных алгоритмах запрещены.

### 2. Нормализация переполненной вставки

Нормализация принимает вставляемое nested-дерево и глубину места вставки. До
создания транзакции выполняется depth-first обход. Пока целевая глубина меньше или
равна 5, parent-child связь сохраняется. Каждый узел, который оказался бы глубже
5, добавляется в sibling-группу уровня 5; его descendants обходятся сразу после
него и добавляются туда же.

Например:

```text
До:    D4 -> E5 -> F6 -> G7, затем H5
После: D4 -> [E5, F5, G5, H5]
```

Такой алгоритм сохраняет читаемый порядок и все блоки, но намеренно теряет только
отношения, которые нарушают лимит. Для обычного inline paste он не запускается.

Интерактивный drag-and-drop не выполняет автоматический flatten: неожиданное
изменение внутренней структуры уже существующей ветки опаснее, чем отказ drop.
Drop cursor и команда nest должны заранее показывать только допустимые цели.

### 3. Три представления документа

```text
Backend FlatBlock[] <-> buildBlockTree / flattenBlocks <-> public Block[]
                                                           <-> Tiptap document
                                                           <-> localStorage JSON
```

- `Block[]` — каноническая публичная модель редактора.
- `FlatBlock[]` — транспортная модель backend и удобная база для diff по ID.
- Tiptap JSON — только внутреннее runtime-представление.
- `localStorage` хранит nested `Block[]`, чтобы локальный snapshot был читаемым и
  загружался без зависимости от backend ordering.

Persistence-модуль не импортируется сериализацией Tiptap. Чистые tree/flat-
преобразования располагаются рядом с публичной моделью или в отдельном модуле
`persistence`, не зависящем от React, DOM и `localStorage`.

### 4. Flatten tree

`flattenBlocks` выполняет depth-first обход. Для каждой sibling-группы он заранее
знает предыдущий и следующий ID и записывает:

```ts
position: {
  before: siblings[index - 1]?.id ?? null,
  after: siblings[index + 1]?.id ?? null,
}
```

`parentId` передаётся рекурсивно. Поле `children` отсутствует в flat-элементе.
Функция проверяет уникальность ID и глубину, чтобы не создавать неоднозначный
backend payload.

### 5. Build tree

`buildBlockTree` сначала индексирует блоки по ID и группирует их по `parentId`, не
полагаясь на порядок входного массива. Для каждой группы строится единственная
цепочка от элемента с `before: null` до элемента с `after: null`. На каждом шаге
проверяются обратные ссылки: если `A.after = B`, то `B.before` должен быть `A`.

Затем выполняются проверки родителей, циклов и глубины. Только после полной
валидации создаются новые `Block` с `children`. Ошибка содержит код, message и
`blockIds`; частичное дерево наружу не возвращается.

Предлагаемые коды: `DUPLICATE_ID`, `MISSING_PARENT`, `PARENT_CYCLE`,
`INVALID_SIBLING_REFERENCE`, `AMBIGUOUS_SIBLING_ORDER`, `MAX_DEPTH_EXCEEDED`.

### 6. Diff и структурные операции

После каждого изменения nested snapshot можно flatten-ить и сравнивать с map
последнего подтверждённого состояния по ID. Структурная часть блока определяется
только тройкой `parentId/before/after`. Content и props сравниваются отдельно.

При переносе ветки меняются связи корня ветки и соседей старой/новой группы.
Descendants не помечаются изменёнными только из-за новой абсолютной глубины: их
непосредственные связи остаются прежними. Конкретное сжатие операций и отправка
на backend будут отдельным изменением.

### 7. LocalStorage boundary

Запись получает актуальный nested `Block[]`, нормализует/валидирует его и сохраняет
JSON. Чтение парсит неизвестное значение, валидирует форму, ID и глубину и только
затем возвращает дерево. Невалидный snapshot не исправляется молча и не смешивается
с `initialBlocks`; вызывающий React-слой выбирает fallback и может сообщить об
ошибке.

## Risks / Trade-offs

- Двойные sibling-ссылки требуют строгой проверки согласованности, зато позволяют
  серверу и клиенту однозначно видеть обоих соседей.
- Flatten уровня 6+ теряет часть исходной иерархии; сохранение depth-first порядка
  делает потерю предсказуемой и не теряет сами блоки.
- Отказ глубоко вложенного drop менее удобен, чем автоматическое изменение ветки,
  но не создаёт неожиданной реструктуризации пользовательских данных.
- Полная валидация перед сборкой имеет стоимость O(n), приемлемую и необходимую
  для безопасного восстановления документа.

## Open Questions

- Нужна ли в будущем миграция старых `localStorage` snapshot с глубиной больше 5
  или достаточно применить ту же нормализацию, что и для paste?
- Должен ли backend принимать обе sibling-ссылки или вычислять одну из них и
  использовать внутренний `sortKey`? Текущий frontend-контракт сохраняет обе.
